Grant Radar tracks funding opportunities for an academic research group — and keeps itself current. The table is curated by hand; the radar sweeps the funders' sites on its own, once a month, and files what it finds as proposals. Nothing written by a machine reaches the table until a human has read the diff and clicked approve.

✎
The table stays human Grants are edited like rows in a spreadsheet: filters, deadlines, one form. Discovery can only propose — approval is a human click on a field-by-field diff, and decided proposals are never deleted: they are the radar's audit log.
📡
The radar sweeps by itself Every night a link monitor checks each tracked call — dead links and changed pages get flagged. Every month an LLM with live web search walks the configured sources, compares them against the table, and proposes new calls and updated deadlines.
⌘
Agents are users too An MCP endpoint exposes the table to AI assistants: search grants, list upcoming deadlines, file proposals into the same queue. Same rules as the in-app radar — propose yes, write never.
plain words Why a radar, and why the machine can't touch the table

The problem. Every research group keeps a list of funding calls somewhere — a shared spreadsheet, a SharePoint list. And every such list rots the same way: deadlines pass, links die, the call that would have been perfect is discovered three weeks too late, and the person who once kept the list tidy has better things to do. The list doesn't fail loudly; it just quietly stops being true.

The fix. Grant Radar splits the work by what each party is good at. Machines are good at patience: checking every link every night, re-reading funder websites every month, never getting bored. Humans are good at judgment: deciding whether a call is actually worth tracking, whether a deadline change is real, whether a scheme fits the group. So the machine watches and proposes; the human decides. The proposal queue is the boundary between the two — everything automatic stops there, and what crossed it and why stays on record forever.

What the AI does and doesn't do. Once a month, an AI model with live web-search access visits each configured source — a funder's website plus a line of hints about what matters to the group. It compares what it finds against the current table and writes up proposals: a new call, with its amounts and deadlines and a link; or an update, say next year's deadline for a recurring scheme. Each proposal carries its reasoning and the page it came from. What the AI cannot do is write into the table: it has no such button, the same way a smoke detector can't rebuild your kitchen. Someone reads the proposal, sees exactly which fields would change, and approves or rejects it.

geek mode Stack, discovery loop, MCP surface

Stack. FastAPI + SQLite + HTMX/Jinja2, JWT cookie auth, Docker behind Caddy. Four working tables: grants, proposals (kind new/update/flag, JSON payload, rationale, confidence, method), sources, users — plus scan_log. Decided proposals are never deleted: light audit log by construction.

Discovery, two engines. A nightly link monitor (httpx, no LLM) fetches every tracked link, hashes the readable text, and files flag proposals for dead links and changed pages. A monthly semantic scan runs one agentic loop per source: claude-opus-5 with the server-side web_search tool, plus a strict-schema client tool submit_proposals the model must call exactly once — schema validation happens at the tool-call layer, and structured outputs stay compatible with web search. The prompt carries the current grants digest so the model distinguishes new from update; pause_turn is handled; a wrong proposal costs one human click, not one corrupted row.

MCP. Streamable HTTP (stateless) mounted at /mcp, six tools: search_grants, get_grant, upcoming_deadlines, list_proposals, propose_grant, propose_update. Auth via X-API-Key header or — for clients that can't send headers — a capability URL /mcp/k/{key}: a middleware validates the key against the same revocable table and rewrites the path, so the MCP app itself stays auth-unaware. Approval is deliberately absent from every API surface: it exists only as a button in this UI. REST for scripts: GET /ono/grants, a compact dump optimized for LLM context windows.
